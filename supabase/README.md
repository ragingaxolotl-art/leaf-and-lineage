# Pattern Lab code-sharing service

Dedicated project: `znrlzfzjbzebojxxswrf` / **breeding beetles**. Council and Crown was not modified.

The deployed `pattern-sumo` Edge Function accepts `create`, `join`, `read`, `start` and `close` actions. The browser sends the publishable API key, a private per-participant capability, and one anonymous beetle packet when creating/joining. Names, notes, other beetles and accounts are not sent. Rooms hold two packets, a common seed, a start timestamp and a match counter. The host starts a shared, deterministic client-side contest; there is no trusted leaderboard.

`schema/pattern-sumo.sql` is the complete deployed database setup. It creates two RLS-enabled tables, revokes all direct table and internal-function access from `anon`, `authenticated` and `PUBLIC`, and grants it only to `service_role`. Internal functions use `SECURITY INVOKER` with a fixed search path. The edge function keeps its privileged key in Supabase-provided server environment variables. It validates the browser publishable key itself, then checks participant capabilities through the database. `verify_jwt=false` is intentional for the modern publishable-key flow; it does not skip the function's own authentication. See [Supabase API-key migration](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) and [Edge Function authentication](https://supabase.com/docs/guides/functions/auth).

Codes use eight cryptographically random characters from a 32-character alphabet, with collision retries. Participant capabilities contain 256 random bits and are stored as SHA-256 digests in the database. No room list is public. Atomic row locks prevent a third participant replacing the guest. Join retries from the same guest capability are supported; the shipped interface disables participant changes while connected. New participants should create a new room. A host can start up to 50 matches before creating a new code.

Codes become unreadable after two hours. Expired rows are physically purged on the next service request. Rate-limit buckets expire after three minutes and store only salted hashes, not raw IP addresses. School users sharing one public IP have separate read/start capability limits; create/join limits are sized for classroom groups. Platform request logging is managed by Supabase separately.

The vendored `functions/pattern-sumo/genetics.js` is the validator deployed with this function. It has the same 80-locus genome definitions as the browser, without depending on browser match-history features. Change/deploy the validator alongside any future genome-schema change.

The repository includes no privileged key. `dist/pattern-lab/sharing-config.js` intentionally contains only the public endpoint and publishable key. For a different Supabase project, apply the SQL setup there, deploy the three function source files, and replace that browser configuration. Keep GitHub Pages serving `dist/`.

Verification covers create/join/read/start, identical seeds and start times on both screens, invalid API keys, invalid genomes, wrong capabilities, third participants, host-only start, closed rooms, and denied public table reads. Security advisors report the informational [RLS enabled without policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) notice for these backend-only tables: default denial is intentional, and the public roles have no grants. Initial unused expiry-index notices are expected for a new, small database; the indexes support expiry cleanup as it grows.

## One-for-one trades

`schema/pattern-trades.sql` and `functions/pattern-trade/` implement the separately deployed `pattern-trade` service in the same dedicated beetle project. The table denies all public/direct access (RLS, no policies, grants only to service_role), with a SECURITY INVOKER RPC and fixed search path. Edge authentication, anonymous genome validation, origin restrictions, hashing and rate limits follow the sumo service. Only the publishable key reaches the browser.

States: open → offered → complete, or cancelled/expired. A guest submits a fixed anonymous packet; only the host confirms. Atomic row locks serialize confirmation/cancellation, and neither cancellation nor retries can undo a completed exchange. Create/join/accept are idempotent for the same capabilities. Complete receipts remain collectable for seven days. Codes are client-generated cryptographic eight-character identifiers; a collision never overwrites another offer. Tokens are private 256-bit capabilities stored locally per class/role/code, not in URLs, exported experiments or the database in plaintext. The two original devices independently collect one-time incoming receipts. Device-local state is checkpointed before making an offer and before applying a completed swap; failed writes leave the pending offer intact. Offline devices can collect later. Changing tanks is blocked while a trade is pending.

This has no central student accounts or authoritative inventory: files can duplicate beetles. It prevents ordinary double-click/retry duplication and accidental disappearance, not deliberate offline cheating. Losing browser storage/private capabilities or abandoning the original tank can prevent collection; save files preserve the beetles but do not include the trade capability. The UI explains the original-device requirement.

Live synthetic tests covered packet validation, denied table reads, wrong tokens, third students, host-only confirmation, immutable guest offers, repeated requests, cancellation and confirm/cancel races, and recovery of completed receipts. Two-screen UI checks also covered refresh recovery and a Keep-slot replacement.

## Battle-rule versions

Apply `schema/pattern-sumo-models.sql` after the original sumo schema. It adds `physics_version` to rooms (existing rooms default to SUMO2) and a service-role-only SECURITY INVOKER wrapper. Each new Edge request passes a validated SUMO2/SUMO3 model; an omitted model preserves old clients as SUMO2. The wrapper locks the same room row before comparing versions and invoking the original capability-checked exchange. A create labels its model in the same transaction. Mixed-rule requests fail before joining or starting, and responses include `physicsVersion`. Public roles cannot call either internal RPC. Existing clients continue using their original physics.

The current Edge deployment uses explicit `import_map_path: deno.json`; replacing a function without this can reuse an obsolete absolute import-map path in the management API. Both SUMO2 and SUMO3 live create/join/start/read/close, shared-seed equality, version mismatch rejection, capability checks and public-table denial were verified after this update. The validator still accepts the same 80 numeric/categorical records; no existing genome is rewritten for the continuous strength-breeding rule.
